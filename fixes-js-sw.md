## S1 — informational (положительная) — НЕ тронуто, сохранено

Механизм версии кэша и очистки в `activate` оставлен как был: `CACHE` по-прежнему версионируется, `activate` удаляет все кэши кроме текущего и вызывает `clients.claim()`. Теперь имя кэша выводится из одной константы: `const APP_VERSION = "21"; const CACHE = "dsh-phone-v" + APP_VERSION;` — поведение идентично прежнему `"dsh-phone-v21"`.

## S2 — medium — fetch-хендлер кэшировал любой GET → ИСПРАВЛЕНО

Было: в кэш попадал каждый GET-ответ (включая opaque кросс-оригинные, 404/500, любые query), без pruning.

Стало:
- `if (url.origin !== self.location.origin) return;` — кросс-оригинные запросы вообще не обрабатываются SW (никаких opaque-ответов в кэше).
- Белый список путей: `isCacheablePath()` — pathname из `ASSETS` ИЛИ расширение из `CACHEABLE_EXT` (js/mjs/css/svg/png/jpeg/gif/webp/avif/ico/json/webmanifest/woff/woff2/ttf/otf/map). Всё прочее (например, произвольные динамические URL) не кэшируется.
- `if (res.ok && res.type === "basic")` — кэшируются только успешные (2xx) базовые same-origin ответы; 404/500 и opaque больше не попадают в кэш и не отдаются офлайн.
- Лимит записей: `MAX_EXTRA_ENTRIES = 50` + `pruneCache()` — после каждого `put` кэш подрезается: записи вне `ASSETS` (insertion order ≈ старейшие первые) удаляются сверх лимита; прекэшированные `ASSETS` не вытесняются никогда. Рост кэша внутри одной версии ограничен.
- `/api/` и не-GET по-прежнему пропускаются (ранние return).

## S3 — medium — рассинхрон версий `?v=19` (HTML) vs `v21`/unversioned (SW) → ИСПРАВЛЕНО со стороны sw.js

Было: `ASSETS` прекэшировал `/app.js` без query, HTML грузил `/app.js?v=19` → две записи в кэше, прекэш не использовался, офлайн-промах после bump версии в HTML.

Стало (единый механизм нормализации в sw.js):
- Введена одна константа версии `APP_VERSION = "21"`; `CACHE` выводится из неё.
- **Нормализация URL**: `normalizeUrl()` убирает query-параметр `v` — `/app.js?v=19`, `/app.js?v=20`, `/app.js?v=21` дают один ключ кэша `/app.js`. Любой bump `?v=N` в HTML больше НЕ вызывает офлайн-промах: запрос с любым `?v=` попадает в одну и ту же запись кэша.
- **Прекэш**: каждый ассет (кроме `/`) загружается как `path?v=APP_VERSION` с `{ cache: "reload" }` (обход промежуточных HTTP-кэшей, гарантированно свежий контент), но кладётся в кэш под каноническим путём без query. Двойного хранения больше нет — ровно одна запись на ассет.
- Fetch-хендлер пишет/читает кэш по нормализованному ключу, поэтому runtime-кэш и прекэш согласованы.

**Что нужно для ПОЛНОЙ согласованности (зона другого агента — index.html):**
1. Сейчас в `index.html` стоит `?v=19`, в sw.js `APP_VERSION = 21`. Благодаря нормализации это уже не ломает офлайн (ключи совпадают), но при желании можно привести HTML к тому же числу — косметически.
2. Рекомендуемая схема на будущее: хранить версию в одном месте и генерировать из неё и `?v=` в HTML, и `APP_VERSION` в sw.js (например, шаблонизация или сборочный скрипт). Пока их два, при релизе нужно менять оба (но рассинхрон больше не фатален).
3. `CACHE` bump'ается при релизе как и раньше — activate вычищает старое.

## S4 — low-medium — install «всё или ничего» → ИСПРАВЛЕНО

Было: `c.addAll(ASSETS)` — один отсутствующий/не-2xx ассет ронял весь install, SW не активировался (нет ни офлайна, ни пушей).

Стало: `Promise.allSettled(ASSETS.map(...))` — каждый ассет fetch'ится и кладётся отдельно; не-2xx бросает ошибку только по своему ассету. Провалы логируются (`console.warn` с причинами), остальные ассеты кэшируются, `self.skipWaiting()` вызывается в любом случае. SW активируется даже при неполном прекэше.

## S5 — low — notificationclick: мёртвая ветка, sessionId не передавался → ИСПРАВЛЕНО

Было: ветка 92–94 и else-ветка делали одно и то же (`c.focus(); return`), `data.sessionId` игнорировался — тап по уведомлению не открывал нужный чат.

Стало:
- Мёртвая ветка удалена; поиск клиента через `list.find(...)` по same-origin.
- Если есть `sessionId` и окно найдено: `target.postMessage({ type: "dsh-open-session", sessionId })` и затем `target.focus()`.
- Если окна нет: `self.clients.openWindow("/#s=" + encodeURIComponent(sessionId))` (или просто `/` без sessionId).

**Что нужно со стороны app.js (другой агент, я не трогал):**
- Слушатель `navigator.serviceWorker.addEventListener("message", (ev) => { if (ev.data && ev.data.type === "dsh-open-session") открыть чат ev.data.sessionId; })`.
- И/или обработка хэша `#s=<sessionId>` при старте приложения.
- Без этого postMessage/hash безопасны (ничего не ломают), но чат не откроется — SW-сторона готова, нужна пара строк в app.js.

## S6 — medium — pushsubscriptionchange → ИСПРАВЛЕНО

Было: `e.newSubscription` игнорировался, старая подписка не отзывалась, узел не уведомлялся (копил мёртвые эндпоинты), `subscribe` без catch → возможный reject внутри `waitUntil`.

Стало:
- `let sub = e.newSubscription || null;` — если браузер дал новую подписку, она используется напрямую, без лишнего `subscribe`.
- Только если `newSubscription` нет: fetch `/api/push/info`, затем `pushManager.subscribe(...)` **обёрнутый в try/catch** (при провале — лог и выход, без reject из waitUntil).
- Перед ротацией best-effort запоминается старый endpoint (`pushManager.getSubscription()`).
- После регистрации новой подписки, если `oldEndpoint && oldEndpoint !== sub.endpoint`, узлу отправляется `POST /api/push/unsubscribe` с телом `{ token, endpoint: oldEndpoint }` — **тот же формат, что использует `disablePush` в app.js (1609–1613)**, так что серверная сторона уже его понимает. Узел больше не копит мёртвые эндпоинты.
- Весь async-IIFE обёрнут в `.catch(...)` — ничто не отклоняется внутри `waitUntil`.

Оговорка: токен по-прежнему передаётся в query `/api/push/info?token=...` — это серверный контракт (app.js:1567 делает так же); перенос в заголовок требует изменения API узла, что вне рамок правки одного sw.js. Отмечено как follow-up.

## S7 — low — фолбэк `caches.match("/")` для любого запроса → ИСПРАВЛЕНО

Было: строка 26 — провалившийся запрос картинки/скрипта получал HTML (`/`).

Стало: `const isNavigate = e.request.mode === "navigate";` — фолбэк на `/` только для navigation-запросов. Остальные при промахе кэша получают `undefined` из respondWith → нормальная сетевая ошибка офлайн (браузер сам обработает), без подмены контента.

## S8 — low — IndexedDB: open на каждую операцию, close только в oncomplete → ИСПРАВЛЕНО

Было: `idbSet`/`idbGet` открывали БД заново на каждый вызов; `db.close()` только в `tx.oncomplete`/`g.onsuccess` — при ошибке транзакции соединение оставалось открытым; `onupgradeneeded` дублировался.

Стало:
- Один ленивый синглтон `openDB()` (`dbPromise`), переиспользуется между вызовами; `onupgradeneeded` объявлен один раз (с проверкой `objectStoreNames.contains`).
- `db.onversionchange` закрывает соединение и сбрасывает синглтон; при провале open `dbPromise` сбрасывается, чтобы следующий вызов попробовал снова.
- Общий `idbTx(mode, fn)`: у транзакции установлены **`oncomplete`, `onerror` И `onabort`** — ошибки транзакций больше не «зависают» молча; `idbSet`/`idbGet` — тонкие обёртки над ним.
- Имя БД/store/версия (`"dsh-phone"`, `"kv"`, 1) не изменились — полная совместимость с `idbSetToken` в app.js и с прежними данными (токен читается как раньше).

## S9 — informational — push без дедупа/троттлинга → ДОБАВЛЕН консервативный дедуп

- `notifyThrottled(key)` с ключом `tag|body|sessionId` и окном `NOTIFY_DEDUPE_MS = 3000`: полностью идентичные уведомления в пределах 3 секунд не показываются повторно (шквал одинаковых событий схлопывается). Map самоочищается от устаревших записей.
- Разные сообщения (другой body/sessionId) не глушатся; `tag` + `renotify: true` по-прежнему заменяют предыдущее уведомление той же группы. Намеренно консервативно, чтобы не потерять важные сообщения.
